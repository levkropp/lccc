Widen loop memory promotion to marching-pointer accumulators (nbody).

src/passes/loop_memory_promote.rs currently promotes a loop memory location to
a register only when the address is loop-invariant and there is exactly 1 load
+ 1 store per iteration. nbody's F64 accumulators (vx/vy/vz per body) round-trip
through memory every iteration: the address is a marching pointer (p, p+stride
across unrolled lanes) or an indexed load with loop-varying base, so promotion
bails. nbody is ~1.6x vs GCC.

Plan:
1. Read loop_memory_promote.rs, identify the invariant-address restriction.
2. Extend analysis to recurrences: address = base + i*stride (affine in the
   induction variable), still exactly one load and one store per lane per
   iteration, no aliasing stores in between.
3. Promote to a scalar register carried across iterations, reload/stored at
   loop boundaries as today.
4. Env-gate (e.g. CCC_NO_MARCH_PROMOTE), benchmark nbody + full suite, commit.

Risk: aliasing safety — must prove no other store in the loop can reach the
promoted location (same as existing analysis, extended to affine addresses).

Status: DONE (commit 57ab50aa). The alias blocker was not really the
1-load/1-store rule but alias precision vs marching stores. Built a linear-form
engine in loop_memory_promote.rs (resolve_lin_form): pointers resolve to
root + Sum coeff*iv + konst + march*t; invariant candidate vs marching store
is disjoint when roots+syms match and the store range marches away. Pass now
also runs to a fixpoint (all eligible pointers promote per run, not just one).

Result: all three bodies[i].v* j-loop accumulators promote to registers.
nbody 1.68x -> 1.60x vs GCC; geomean 0.597 -> 0.581. 18/18 byte-identical.

Follow-up exploration (2026-08-18, commit 51285cd5):
- Extracted the linear-form engine to src/passes/alias.rs (shared).
- GVN: F32/F64 loads now CSE (float exclusion predated backend F64 copies).
  Benchmark-neutral on the suite, principled parity fix.
- DEAD END: alias-aware selective store invalidation in GVN (keep load CSE
  entries alive across provably-disjoint stores) — geomean-neutral A/B,
  possible regressions (struct_copy), high complexity. Reverted.
- DEAD END: affine LICM hoisting of invariant global/GEP loads past
  provably-disjoint stores (bodies[i].x/y/z out of the j-loop) — 60% nbody
  REGRESSION: hoisted FP values exhaust the FP register pool and every FP
  intermediate starts bouncing through stack+GPR. Our regalloc cannot absorb
  extra FP live values in hot loops. Reverted.
- Remaining nbody gap (~1.5x): the FP register pool is the binding constraint;
  next real wins need better FP regalloc/spill policy, or (x,y)-pair NEON
  vectorization of the struct components like GCC does.
